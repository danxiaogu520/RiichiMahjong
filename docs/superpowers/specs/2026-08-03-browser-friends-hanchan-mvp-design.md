# 浏览器熟人房间半庄 MVP 设计

- 日期：2026-08-03
- 状态：已完成设计确认，待用户审阅书面规格
- 目标：让四个朋友通过浏览器和房间码稳定完成一局四人立直麻将半庄

## 1. 背景与目标

项目已经具备 Rust 规则引擎、AI、本地终端客户端、HTTP/WebSocket 服务、房间管理、会话重连和 Tauri/Web 前端基础。下一阶段不扩张到完整游戏平台，而是把现有能力收束成一条可发布的熟人开黑闭环。

首发用户从固定公网网址进入，输入昵称和房间码，与三名朋友进入同一房间并完成一局半庄。首发优先保证进入门槛低、对局流程完整、服务端状态权威、断线和超时行为可理解。

## 2. 产品范围

### 必须支持

- 创建房间、加入房间、退出房间和房间码展示/复制。
- 四个座位、昵称、准备状态和房主开始操作。
- 摸牌、出牌、立直、吃、碰、杠、荣和、自摸和流局。
- 服务端倒计时、超时自动摸切或自动 Pass。
- 桌面浏览器中的玩家视角牌桌、手牌、牌河、宝牌、点数和行动提示。
- 断线自动重连、原座位恢复和当前行动恢复。
- 半庄结束原因、最终点数、排名和结果页面。
- 固定公网服务的 HTTPS/WSS、健康检查和基本日志。

### 明确不包含

- 注册登录、持久化账号和个人资料。
- 公开匹配、排位、段位和长期战绩。
- 聊天、表情、观战和牌谱分享。
- 手机端专门布局和移动端专用 UI。
- 多服务器水平扩展、数据库和服务器重启后的房间恢复。
- 运行时规则切换。

## 3. 用户流程

1. 玩家打开固定公网网址。
2. 玩家输入昵称，选择创建房间或输入房间码加入。
3. 服务端分配座位并返回临时 token。
4. 玩家在等待房间查看四个座位和准备状态。
5. 四人准备后，房主开始半庄。
6. 客户端通过 WebSocket 获取玩家视角快照和行动提示。
7. 玩家提交服务端提供的合法行动，直到局或半庄结束。
8. 客户端显示结果，并允许返回首页或创建新房间。

## 4. 架构与数据流

继续使用现有单向依赖：

```text
浏览器客户端
    │ HTTP + WebSocket
    ▼
riichi-server
    ├── 房间、座位和临时 token
    ├── WebSocket 连接与重连
    └── GameSession 生命周期
            │
            ▼
riichi-engine
    ├── GameState 和规则状态机
    ├── 行动合法性
    └── 结算与排名
            │
            ├── riichi-core
            └── riichi-logic
```

- 服务端是唯一权威；浏览器不判断合法性、不计算点数、不推进牌局。
- 一个房间对应一个 `GameSession`，由单一任务顺序修改 `GameState`。
- HTTP 负责创建/加入/准备等房间操作；WebSocket 负责牌局事件和玩家行动。
- `riichi-proto` 负责消息边界、序号、命令标识和玩家视角投影。
- 服务端仅发送接收者可见的数据，隐藏手牌和摸牌不能出现在其他玩家消息中。
- 首发使用内存房间；对局结束后释放房间和会话。

典型数据流为：

```text
创建/加入房间
    → 获取座位与临时 token
    → 四人准备
    → 创建 GameSession
    → 推送玩家视角快照
    → 客户端提交行动
    → 服务端校验 command_id / expected_seq / 权限
    → engine 推进状态
    → 生成逐玩家视角事件
    → 推送给四名玩家
    → GameOver 后释放会话
```

## 5. 可靠性规则

### 超时

- 服务端负责计时，客户端倒计时只用于展示。
- 轮到玩家出牌超时，默认执行摸切；状态异常时选择一个合法舍牌。
- 荣和/鸣牌响应超时，默认执行 `Pass`。
- 超时动作进入权威事件流，所有玩家看到同一结果。

### 重复与过期操作

每个客户端命令携带 `command_id` 和 `expected_seq`。服务端拒绝重复、过期、身份不符或不合法的命令，不推进牌局，并返回结构化 `CommandRejected`。客户端显示简短原因，必要时请求最新玩家视角快照。

### 断线重连

- 客户端采用指数退避自动重连。
- 临时 token 绑定原座位，重连后替换旧连接。
- 旧连接的行动转发任务必须失效，不能继续提交命令。
- 重连后发送最新状态、尚未发送的事件和当前行动提示。
- 对局结束时直接展示结果；服务器重启导致内存房间消失时，显示“房间已结束”并停止无限重试。

### 用户可见错误

错误分为网络错误、操作错误和房间错误三类。界面不直接暴露 Rust、WebSocket 或内部 channel 错误，而是显示连接中断、动作已过期、房间已满、对局已开始等可行动的提示。

## 6. 浏览器端状态

### 进入页

显示固定服务器状态、昵称输入、房间码输入以及创建房间入口。首发不显示服务器地址配置。

### 等待房间

显示房间码复制按钮、四个座位、昵称和准备状态。玩家可以准备、取消准备或退出；四人准备后房主可以开始。

### 牌桌

显示局数、场风、剩余牌数、宝牌、点数、四家牌河、自己的手牌、当前行动玩家、倒计时和连接状态。所有操作按钮由服务端候选列表驱动，只展示当前玩家合法的出牌、立直、鸣牌、杠、荣和、自摸及流局操作。

### 结果页

显示结束原因、四家最终点数、排名、击飞或特殊终局信息，并提供返回首页和重新开房入口。不加入聊天、观战和复杂动画。

## 7. 规则发布策略

继续使用项目当前固定规则，不提供运行时规则切换。发布前必须修复并测试会影响正常半庄推进、响应优先级、结算或玩家公平性的规则缺口，包括西入/all-last、响应等待、多家荣和、四杠散了和流局时序等。极少见且不阻断正常对局的边界规则可以作为明确记录的后续任务，但不能通过调用方临时分支绕过引擎。

## 8. 测试与发布门槛

### 自动化测试

- 引擎：正常半庄、行动合法性、立直/鸣牌/和了、流局、终局、计分、排名和关键规则回归。
- 会话：超时摸切/Pass、重复命令、过期命令、断线重连、旧连接失效、GameOver 清理。
- 协议/服务端：房间生命周期、token 与座位绑定、隐藏信息投影、序号/快照恢复、身份校验和资源释放。
- 前端：TypeScript 类型检查和生产构建。

### 发布验收

使用四个独立桌面浏览器窗口连接公网服务，完成创建房间、加入、准备、完整半庄、一次断线重连、一次超时处理和最终结算。发布前还必须确认 HTTPS/WSS、健康检查、服务日志和文档与实际行为一致。

## 9. 后续方向

首发稳定后，再按用户反馈选择手机适配、牌谱回放、聊天、观战、持久化战绩、公开匹配或规则变体。它们不应提前进入本次 MVP，以免削弱完整半庄闭环。
